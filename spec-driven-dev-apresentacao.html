spec-driven-dev

Um harness de Spec Driven Development para qualquer stack: do contexto do projeto ao código validado — nos testes, na tela e na revisão.

Como usar o plugin · passo a passo

Apresentação do fluxo completo: inicialização, especificação, execução com verificação de interface, manutenção e segurança.

O PRINCÍPIO

O agente implementa.
A validação decide.

Nenhuma tarefa é dada como pronta pelo relato do agente. Ela passa por um teste rodado por fora, pela tela num navegador real e por uma revisão feita por quem não escreveu o código.

Fio condutor de todo o harness: o 'pronto' é sempre verificado mecanicamente, nunca declarado.

VISÃO GERAL

Quatro etapas, um fluxo

1

Inicialização

/init descobre como o projeto funciona e o que será construído.

2

Especificação

/plan transforma uma fatia em spec aprovada e plano de tarefas.

3

Execução

/implement com você, ou ralph.sh sozinho, com os mesmos gates.

4

Manutenção

/revise aplica mudança de requisito; /review revisa sob demanda.

Tudo o que o harness sabe do projeto fica em .sdd/, versionado junto com o código.

ETAPA 1 · INICIALIZAÇÃO

init:context — como se desenvolve aqui

STANDARDS.md

Stack, arquitetura, convenções, testes, interface, segurança, git e regras para agentes. Cada regra com origem: [observado] [decidido] [esqueleto].

config.json

Modo, comandos (um por valor ou lista — nunca &&), paths.frontend, ambiente de verificação e preferências lembradas.

codebase.md

Só em projeto existente: retrato do sistema atual — módulos, entidades, interfaces e regras com arquivo:linha.

Seção Interface

Layout padrão e onde fica a navegação, biblioteca de componentes, padrão de formulário, retorno após ação, idioma da interface e das mensagens, tela de referência.

Barreiras

Regras deny no .claude/settings.json (segredos, git push) e o .mcp.json do navegador de verificação.

Entrevista de produto

Propósito, atores e permissões, conceitos com números, fluxos com caminhos infelizes, fronteira do MVP. O que ficar indefinido vira questão em aberto.

Roadmap em fases

Cada fase é uma fatia entregável, do tamanho de um plano, com dependências, entrega verificável e a Entrada para /plan pronta.

## Fase 2: Criação e envio
- **Status**: pendente → planejada (slug) → implementada (slug)
- **Cobre**: F-01, E-01, E-02, E-03
- **Entrada para /plan**: slug `criacao-e-envio` — ...

Questão respondida numa spec volta marcada como resolvida no project.md, e o bloqueio sai da fase.

ETAPA 2 · ESPECIFICAÇÃO

A spec: linguagem que dá para testar

RF-01 QUANDO o colaborador envia a solicitação, O sistema DEVE ...
RF-02 SE o valor passar de R$ 500, ENTÃO O sistema DEVE ...
RF-03 ENQUANTO a solicitação estiver em análise, O sistema DEVE ...
RNF-01 (segurança) apenas o autor e o gestor da área acessam a solicitação
CA-06 (RNF-01) usuário de outra área recebe acesso negado e nenhum dado
CA-07 (RF-01) colaborador chega à tela pelo menu lateral e vê o toast ao enviar
[CLARIFICAR] reembolso parcial de item reprovado? Opções: sim | não

Três formas de requisito

Evento, exceção e estado. Sempre com resposta observável.

Interface é requisito

Ponto de entrada, retorno após a ação, estados vazio/erro e o que a tela mostra em cada estado terminal.

Segurança é requisito

Área sensível gera RNF com critérios negativos.

Ambiguidade nunca vira palpite: vira CLARIFICAR com as opções em jogo. Tela que ninguém alcança é defeito — e só vira teste se estiver escrita aqui.

ETAPA 2 · ESPECIFICAÇÃO

O plano: cada tarefa é um bloco

- [ ] T-03 Tela de detalhe da solicitação
  - Cobre: CA-02, CA-06
  - Depende: T-01
  - Arquivos: `resources/js/pages/expenses/show.tsx`
  - Valida: `php artisan test --filter Detalhe`
  - Sensível: sim — autorização por área
  - Interface: `/despesas/{id}` — referência: `.../index.tsx`

- [ ] T-09 [humano: verificação] conferir o recibo impresso

Cobre liga a tarefa aos critérios da spec.

Valida só usa comandos do config.json.

Sensível ativa o checklist de segurança.

Interface aciona a verificação no navegador e aponta a tela de referência.

[humano] é ação, nunca decisão — decisão volta para a spec.

ETAPA 3 · EXECUÇÃO

Execução: cada tarefa passa por cinco portas

1

Implementar

Só nos arquivos declarados. Plano, spec e config são protegidos.

2

Testar

sdd-test-agent escreve testes a partir dos critérios, inclusive os negativos.

3

Gate mecânico

O comando de teste roda por fora do agente. Vale o código de saída.

4

Interface

Tocou o frontend? sdd-ui-agent percorre a tela num navegador real.

5

Revisão

sdd-review-agent, somente leitura. Só APROVADO explícito aprova.

Falhou?

Até 3 ciclos de correção, com a causa real entregue ao agente como dado.

Passou?

Varredura de segredos → marca [x] → log → commit. Nessa ordem.

/implement e ralph.sh seguem exatamente o mesmo contrato e são intercambiáveis no meio de uma feature.

ETAPA 3 · EXECUÇÃO

Verificação de interface: a tela é testada na tela

Como funciona

O script recria o banco de verificação, sobe um servidor próprio e o sdd-ui-agent abre a aplicação pelo Playwright MCP: chega à tela pela navegação, percorre os critérios com cada ator, captura desktop e mobile e compara com a tela de referência.

O que reprova

Critério que não se completa pela tela, erro no console, requisição 4xx/5xx inesperada, retorno ou estado que a spec exige e não aparece, tela inutilizável em mobile. Diferença visual é ressalva, com captura.

Ambiente separado do de desenvolvimento, com dois usuários de cada papel — é isso que torna os critérios negativos verificáveis na tela. Sem ambiente configurado, a tarefa não passa; --sem-ui pula e registra.

ETAPA 3 · EXECUÇÃO

Parou? Retomar é rodar de novo

Corrigir à mão

Revise o diff, corrija, commite e rode ralph.sh <slug>. Ele segue da próxima pendente.

Descartar a tentativa

--descartar-tentativa limpa o que ficou e refaz a tarefa. Sempre pede confirmação humana.

Seguir sem commit

--allow-dirty mantém o trabalho parcial e desliga o commit automático.

O estado vive no disco: marcações no plano, um commit por tarefa e o log em .sdd/logs/. Ao parar, o script imprime estas opções com os comandos prontos.

ETAPA 4 · MANUTENÇÃO

/revise — mudança de requisito como diff

Requisitos funcionais
  + RF-05 QUANDO o valor ultrapassar R$ 1.000, O sistema DEVE exigir o diretor
  ~ RF-02 antes: ... reprovar → depois: ... devolver para ajuste
  - RF-03 (obsoleto) aprovação única para qualquer valor

Nada escrito antes do OK

Diff, perguntas e aprovação, como no /plan.

Concluídas não são desmarcadas

Viram tarefas de ajuste com Revisa: T-03.

Histórico preservado

Obsoletos vão para o fim da spec; a fase volta a planejada.

ETAPA 4 · MANUTENÇÃO

Os três agentes

sdd-test-agent

Lê a spec antes do código e escreve os testes a partir dos critérios. Escolhe o nível pelo tipo do critério. Prova que o indevido é recusado. Só escreve arquivos de teste; nunca instala nada nem corrige a implementação.

sdd-ui-agent

Modelo sonnet, só leitura e navegador. Abre a aplicação no ambiente de verificação, chega à tela pela navegação, captura desktop e mobile e devolve INTERFACE: APROVADA ou REPROVADA com evidência.

sdd-review-agent

Modelo haiku, só Read, Grep e Glob, recebe o diff pronto. Por tarefa e por feature: critérios, escopo, padrões, teste tautológico e checklist de segurança. Bloqueia só com evidência em arquivo:linha.

/review <slug> ou /review --diff <range> roda a revisão sob demanda, inclusive em código escrito fora do harness.

spec-driven-dev · Agentes · 17

Separar autor de verificador é a base: quem escreveu reaplica o mesmo raciocínio que produziu a falha.

PROTEÇÕES

O que é estrutural fica com máquina

sdd-check.sh standards | project | roadmap
sdd-check.sh spec|plan|revise <slug>

Os comandos chamam o validador no fim de cada etapa, e você pode rodá-lo à mão. Falha encontrada é corrigida antes de encerrar.

Seções obrigatórias, IDs únicos e existentes, todo critério com tarefa, dependências só para trás, formato do bloco de tarefa, motivo de [humano] válido, decisão disfarçada de tarefa, comando encadeado no config, obsoleto de volta na spec.

Regra em texto no fim de um comando longo é pulada; script não.

spec-driven-dev · Validação · 18

Extrair as validações para script foi a resposta a uma regra que o modelo ignorou na prática. Os dois scripts têm suíte de testes própria, que não gasta tokens.

PROTEÇÕES

Segurança em duas frentes

Do próprio harness

Arquivos protegidos restaurados se o agente mexer · revisão e interface fail-closed · revisor sem shell · permissões restritas · varredura de segredos antes do commit · comandos de gate listados antes de rodar · descarte exige humano.

Do código produzido

Requisito: RNF de segurança com critérios negativos. Teste: o indevido é recusado. Revisão: checklist OWASP agnóstico de stack. Gate: auditoria e análise estática no fecho.

Limite honesto: a varredura só pega padrões conhecidos de chave, e o log guarda a saída do modelo em texto puro, fora do git.

spec-driven-dev · Segurança · 19

O harness parte do princípio de que o agente pode errar ou ser manipulado pelo que lê. Por isso as garantias são mecânicas.
